# PersonaX 来了：我把 Z 哥「拆了」

> *拆完之后的感受：爽，但真不适合所有人。*

---

## 先交代背景

四个月前我做了个叫 **zettaranc-skill** 的东西，初衷很简单——让 Z 哥（万千）的投资思维框架能跑在 AI 里，帮我看看票、聊聊天。

那时候我完全不知道自己想要什么，想到哪写到哪。一个 `modules/` 目录里，数据库操作、指标计算、策略识别、话术生成、prompt 模板全塞在一起。连 Z 哥的知识库，都是直接丢在几个 markdown 文件里，和 Python 代码平起平坐。

结果呢？

越往后迭代越难受。想加一个新指标？得改五个地方。想换个 LLM 提供商？prompt 模板散落在三个文件里。想接入别的数据源？耦合到让人想哭。最离谱的一次，我想给项目加财报分析能力，发现连「工具代码」和「Z 哥的说话风格」都缠在一起，根本拆不开。

我懂了：**不是代码不行，是架构「长歪了」。**

---

## 所以有了 PersonaX

这次我干了件程序员最爱干的事——**解耦**。

不是小修小补，是彻底的重构。如果旧项目是一团揉在一起的毛线，PersonaX 就是一盒乐高——每一块都有自己的位置和接口。

### 三层解耦到底是什么意思？

用大白话说：以前 Z 哥的「B1 买点判断」和「Z 哥说话方式」是绑死的，想把这个判断逻辑给别的角色用？复制粘贴改一遍。

现在，**工具只管计算，人格只管说话，编排只管调度**。

一条查询进来，整个链路是这样的：

```
用户提问
    ↓
Router（关键词/意图识别）
    ↓
├─→ Knowledge（ChromaDB 语义检索）─┐
├─→ Tools（技术指标/财报分析）─────┼→ SignalAggregator
├─→ Strategies（人格专属策略）─────┘
    ↓
ResponseGenerator（LLM 融合）←── personality.md
    ↓
Persona Analysis（人格化自然语言回答）
```

**Tools 层**（`tools/`）：纯计算，无状态。输入 DataFrame，输出 ToolResult。KDJ 指标不知道 Z 哥是谁，财报分析器也不知道说话要带什么语气。它们是「哑巴工具」，只负责算。

**Orchestration 层**（`orchestration/`）：调度中心。Router 决定走哪条路——问基本面就调财报工具，问技术就调指标工具，问知识就查向量库。ToolCache 避免重复计算，SignalAggregator 处理多个信号打架的情况（比如 KDJ 说买，MACD 说卖，怎么综合？）。最后 ResponseGenerator 把结果喂给 LLM。

**Personas 层**（`personas/`）：人格配置。一个角色就是一个文件夹，里面三个文件：
- `personality.md`：身份卡 + 表达 DNA。Z 哥会说「少妇战法」、「只输一根 K 线」，财务分析师会说「ROE 持续性」、「有息负债率」。
- `overrides.yaml`：阈值覆盖。Z 哥的 B1 触发条件是 J 值 < 13，但你要新建一个「保守版 Z 哥」，改成 J 值 < 10 就行，不用改代码。
- `strategies/`：专属策略集。自动注册发现，新增一个 `.py` 文件就生效。

**新增一个角色有多简单？** 创建 `personas/你的名字/` 目录，丢进去这三个文件，Engine 自动识别。不需要改任何 Python 代码。

### 还有一个很重要的设计：行为边界

每个角色的 `personality.md` 里，都有一个「诚实边界」章节。明确规定了**这个角色不会做什么**。

比如 Z 哥：
- 「不能预测股价」—— 只做应对，不做预测
- 「信息截止到调研时间（2026-04-18）」—— 不会假装知道之后的事
- 「公开表达 ≠ 真实想法」—— 承认语料深度有限
- 「知行合一是最大瓶颈」—— 不会替你执行止损

财务分析师：
- 「不能预测股价」—— 财报分析判断企业质量，不预测市场情绪
- 「不能识别所有造假」—— 专业财务造假需要审计手段
- 「单一指标不说明问题」—— 不会用 ROE 一个数字下结论
- 「无法替代专业审计」—— 分析是筛查，不是确证

这意味着：**PersonaX 里的每个角色，都清楚自己什么能做、什么不能做。** 不会为了回答而编造，不会为了看起来厉害而越界。边界写在人格配置里，是架构的一部分，不是 prompt 里的一句「请诚实」。

当你问 Z 哥「明天大盘怎么走」，他会告诉你「我不预测，只会应对」。当你问财务分析师「这只票明天能涨吗」，他会告诉你「我只看财报，不预测股价」。

这种「知止」的设计，在 AI 产品里反而稀缺。

### 知识库彻底独立

旧项目里，Z 哥的知识文档和交易体系是写死的。PersonaX 把知识库完全抽出来：

- `knowledge/` 负责向量检索（ChromaDB + 通义千问 Embedding），适合结构化知识
- `wiki_query.py` 支持非向量化查询（关键词+标签匹配），适合个人 Obsidian vault，不需要 Embedding API
- `registry/wiki.yaml` 配置知识库路径，公共 wiki 和个人 wiki 分开管理

这意味着：你可以有自己的「私人知识库」，和项目的公共知识库并行存在，互不干扰。

### 还有这些

- **财报分析工具链**：自动下载上市公司年报/季报 → PDF 提取 → LLM + 规则双引擎分析。LLM 可用时用通义千问做深度分析，LLM 不可用时自动降级为规则评分（ROE/毛利率/负债率/成长性四维打分），**任何情况下都能输出可靠结论**。
- **多轮诊断问诊**：3 轮 4 路线（A 持仓诊断 / B 买点确认 / C 逃命判断 / D 长线配置），ConversationManager 维护对话状态，像医生一样逐层问诊。
- **多 LLM 后端**：DashScope / MiniMax / Kimi / Bailian / Anthropic，通过环境变量自动识别，一键切换。
- **行为边界内建**：每个角色的「诚实边界」写在 personality.md 里，超出能力范围的问题明确拒绝回答
- **114 项测试**：从架构集成到知识库检索，每个模块都有测试兜底。

## 但我要泼一盆冷水

**PersonaX 的上手难度，比旧版高不少。**

旧版 skill 是个「开箱即用」的东西：装个依赖、配个 token、丢进 Claude Code 就能聊。飞书、Slack、各种 CLI 通道都通，上班摸鱼开个飞书窗口跟 Z 哥唠嗑，老板还以为我在高强度对需求。

PersonaX 不是。

它需要你理解三层架构各自的职责，需要配置环境变量、初始化知识库、理解注册表机制。它更像一个「框架」而不是一个「插件」——灵活了，但也复杂了。

**所以我说实话：大多数人，用旧版 skill 就够了。**

---

## 那我为什么还做？

两个原因。

**第一，我想看看到底能做到什么样子。**

旧版是「先开枪再画靶子」，这次我想「先把靶子画好」。三层解耦不只是听起来高级，它意味着以后加一个新的人格角色，只需要创建三个配置文件；加一个技术指标，只需要在 `tools/quant/technical/` 里实现一个纯函数；换一个 LLM 提供商，只需要改一个环境变量。

这是「预留空间」——给未来的自己留的。

**第二，我没打算放弃旧版。**

说实话，我自己后面肯定还会继续用 skill。飞书通道太方便了，IM 全打通，随时随地掏出手机就能问一句「Z 哥，这只票怎么看」。PersonaX 目前更适合在本地跑脚本、做深度分析，不是同一个场景。

两个项目会并行存在：
- **zettaranc-skill** → 日常随问随答，摸鱼神器，IM 通道全覆盖
- **PersonaX** → 深度分析、扩展开发、探索架构边界

## 最后

PersonaX 是我的第二次练手。

第一次是「不知道自己要什么」，第二次是「知道自己要什么，但很难」——难的不是写代码，是克制住「把东西揉在一起图省事」的冲动，老老实实拆清楚、定义接口、写测试。

如果你也做过那种「越写越恶心」的项目，你懂我在说什么。

**这个项目目前还没有开源。** 原因很简单：还没完全跑通。目前只上线了 Z 哥一个人格，我还有不少后备队员等着上场——财务分析师只是搭了个架子，后续还有 BOSS 墨、芒格、Naval 等等一堆角色在排队。

现在我也在测试一个更有意思的东西：**多人对话**。

不是那种「一个 AI 假装多个人」的廉价表演，而是让多个 Agent 真正协作——Z 哥看技术面，财务分析师看基本面，各自用各自的认知框架分析，然后由编排引擎综合输出。关键是**不污染上下文**：每个 Agent 只看到自己的输入和输出，不会互相干扰。

这种模式如果跑通了，会比单角色问答有趣得多。但老实说，我还在恶补 Agent Team 的玩法，距离能用还有一段距离。

所以现阶段，**这个项目真的只是半成品**，不适合任何人拿去用。如果你只是想找个 AI 聊聊天看看票，旧版 skill 更香。

至于 PersonaX 能走多远？我也不知道。但至少这次，底子是正的。
